# 微读墨记内置交付形态比较

本文比较两种交付形态：甲，在微读墨记仓库开专用分支产出内置特供版，卡片以小组件形式嵌入十雨桌面；乙，升级原版微读墨记对外提供组件宿主协议与数据接口，十雨桌面作为宿主消费。所有判断以两侧当前源码为准，行号来自工作区实际文件。

## 一 事实基线

微读墨记：`D:\WorkBuddyStation\WereadMoji\weread-widget`，HEAD `5c67da6`，tag `v1.3.1-beta`，`LICENSE` 为 MIT（1KB）。纯 Java，无 Gradle，构建入口 `tools/build.sh`（`README.md:234-243` 说明不用 Gradle 的原因）。包名 `com.inkread.weekread`（`app/src/main/AndroidManifest.xml:3`），`targetSdk=30`、`minSdk=23`（`tools/build.sh:221-222`），资源编译用 android-33（`tools/build.sh:121`），Java 层 `--release 8`（`:241`），dex `--min-api 23`（`:250`），签名使用 `_keys/wereadmoji-release.keystore` 与 apksigner（`:277`、`:311`），发布由 `.github/workflows/release.yml` 在 tag 上建 Release 并挂 APK。

十雨桌面：`D:\DSHStation\OctoberLauncher`，Kotlin 多模块 Gradle，`applicationId com.shuiyu.octoberrain`（`app/build.gradle.kts:14`），`minSdk 26`、`targetSdk 35`（`gradle/libs.versions.toml`），release 沿用调试签名（`app/build.gradle.kts:37`），`versionCode 20`、`versionName "1.0.0"`（`:23-24`），开启 R8 与资源裁剪（`:32-34`）。

两侧都已实现微信读书网关客户端，且指向同一地址：微读 `net/WereadApi.java:41-42`（`https://i.weread.qq.com/api/agent/gateway`，`skill_version 1.0.4`）；十雨 `feature/content/.../data/WereadClient.kt:49-50`（同一网关，`skill_version 1.0.5`），密钥来自用户填写（`core/common/.../Models.kt:299-301` 的 `wereadApiKey`）。十雨已有八个微读类组件（`WidgetCatalog.kt:98`、`:109`、`:120`、`:131`、`:142`、`:153` 等，含封面、热力、书签、笔记、统计、账单、排行、指纹），这些组件的数据由十雨自行拉取，不经微读墨记。

微读墨记的差异价值在本地派生与历史：`core/StatsStore.java`（374 行）、`core/NoteStore.java`（1974 行）、`core/BillScheduler.java`（826 行）、`core/BillStore.java`（206 行）、`core/CardPrefs.java`（723 行），以及卡片渲染子系统（`feature/CardRenderer.java` 2210 行、`feature/WeekCardView.java` 736 行、`a11y/CardContentController.java` 705 行、`a11y/OverlayController.java` 889 行、`a11y/CardA11yService.java` 553 行、`a11y/A11yEventRouter.java` 856 行、`core/CardSpec.java` 392 行、`feature/CardLayout.java` 298 行、`feature/CardInteraction.java` 210 行）。上述清单合计约 13600 行，是两条形态的成本主体。

## 二 两种形态的实现边界

甲的实现边界：微读仓库专用分支保留完整应用，把卡片视图及其数据层作为「内置件」交付；十雨新增一个组件包装层，把卡片视图放进 `WidgetView.draw` 的矩形内。因为组件协议在进程内（`core/widget-api/.../WidgetApi.kt:18-45` 的 `WidgetView`，`draw(canvas, width, height)`），甲必须把 Java 代码编译进十雨；十雨当前 Gradle 配置只编译 Kotlin（`gradle/libs.versions.toml` 的插件仅有 `kotlin-android` 等），需要新增 Java 源集或独立 Java 库模块。

乙的实现边界：微读保持独立应用，新增对外的只读数据出口（内容提供者或绑定服务），十雨新增一层的桥接客户端，把数据喂给自绘组件。卡片视觉不在乙的范围内，乙交付的是数据；若要求卡片外观一致，仍需在十雨侧重绘，按现有八个组件的做法扩展。

## 三 代码归属、构建链与版本管理

甲：卡片代码归属微读仓库专用分支，构建链仍是 `aapt2 + javac + d8 + apksigner`，其产物只能以源码或 jar 形式进入十雨，再由 Gradle 二次编译。版本关系变成「十雨版本携带某次微读快照」，微读上游每发一版，十雨要重做一次移植与回归；分支与主干长期并行，`git log` 已显示单文件改动频繁（`CardRenderer.java` 2210 行、`NoteStore.java` 1974 行），合并成本按改动行数计。

乙：代码归属清晰，微读只在自身仓库演进，十雨只依赖一个版本化的数据契约。构建链各自独立，没有二次编译；版本管理退化为「协议版本号 + 最低支持版本」，与十雨现有的配置迁移策略同类（`ConfigMigration` v7）。

## 四 签名、包名、共存与升级

两侧包名不同（`com.inkread.weekread` 与 `com.shuiyu.octoberrain`），签名不同（微读 release 私钥在库外，十雨 release 用调试签名），因此两应用天然共存，安装与覆盖互不影响。

甲：十雨包内含卡片代码与数据层。若沿用微读原 SharedPreferences（`core/CardPrefs.java:69` 的 `cfg`）与内部文件位置，十雨进程内会产生一份与独立微读不同的数据副本；用户已有的阅读历史、账单与笔记需要一次性导入，导入后两侧数据分叉。若改为只读独立微读的数据文件，则受分区存储与应用私有目录限制，不可行。十雨的组件因此只能使用「新副本」，与用户既有微读数据割裂。

乙：数据归属仍在微读，签名与升级方式不变，微读照常发版；十雨升级不触碰微读数据。两应用共存下，用户数据只有一份。

十雨的 R8 需要为新组件类补保留规则（现规则只到 `app/proguard-rules.pro:51-52` 的接口实现保留，叠加 `:14-27` 的六个模块类），甲的内置卡片类若无反射入口不必额外保留，但 Java 与 Kotlin 混编后混淆边界需逐类确认。

## 五 数据共享通道的三项选择与代价

内容提供者：微读新增 `ContentProvider`，把 `StatsStore`、`NoteStore`、`BillStore` 的派生结果编码为 JSON；十雨用 `ContentResolver` 读取。微读侧约 150 至 250 行（免 AndroidX，手写 Uri 匹配与游标），十雨侧约 120 至 180 行（数据模型与解析）。可加自定义 signature 级权限限制访问方。代价是跨进程一次查询，数据为快照，需配合 `ContentObserver` 或定时刷新；两应用都需在线下共存。

文件导入：微读导出 JSON 到公共目录，十雨读取。两侧各约 80 至 120 行，但需要用户手动操作，无法自动刷新，只适合一次性迁移，不适合日常同步。

服务绑定：微读提供绑定服务与 AIDL 接口，十雨即时读取并可接收推送。约 300 至 400 行（AIDL 与 Parcelable，或手写 Binder），后台绑定受 Android 14 前台服务限制，且十雨的生命周期要跟随绑定状态。仅当需要「微读数据变化即时反映到十雨组件」时才值得付这份成本。

甲不需要任何跨进程通道：数据在同一进程内直调，代价转移到「数据副本与导入」以及维护两套存储。乙的内容提供者是成本最低的可用方案。

## 六 无障碍输入与悬浮窗在真实组件宿主中的替代成本

微读卡片是 `TYPE_ACCESSIBILITY_OVERLAY` 窗口（`feature/OverlayWindow.java:25-27`），靠无障碍服务判断当前是否在桌面、第几页（`a11y/ElaHomeProbe.java`、`a11y/TomoPageGate.java`、`a11y/A11yEventRouter.java`），并靠固定的 480×800 屏幕坐标摆位（`core/CardSpec.java:39-49`，卡片 368×346，展开高度到 750）。这套机制在十雨宿主内全部作废：十雨的组件按宿主给出的矩形绘制（`WidgetApi.kt:32-45`），不需要判断桌面页，也不需要固定 480×800。

甲由此获得主要收益：卡片不再要求无障碍权限与桌面探测，位置由 `DesktopMetrics` 计算，用户可在宫格或列表形态下使用。代价是卡片交互要重新映射：`CardRenderer` 内部按 368×346 写死了大量点按区域（`:238` 之后的十余个 `draw*` 方法），宿主矩形变化时需要重排坐标。若把 `WeekCardView` 整体放进组件，触摸由 `WidgetView.onClick(x, y)` 转发，工作量集中在坐标换算与刷新按钮、设置入口、翻页按钮三类入口。

乙不改变卡片形态，微读仍以无障碍悬浮窗呈现；十雨的组件只显示数据，用户想查看卡片细节仍需打开微读。无障碍权限需求仍由微读持有。

十雨自身已声明无障碍服务（`app/src/main/AndroidManifest.xml:78-87` 的 `OverlayAccessibilityService`），甲不能减少十雨已请求的能力，只能减少微读侧的权限依赖。

## 七 性能与内存

甲：单进程，卡片渲染与数据层和十雨同一进程。源码规模约 13600 行，release 包预计增加 0.4 至 0.6MB（当前 release 包约 566KB，Java 代码经 R8 后压缩尚可）；内存侧多出 `NoteStore`（1974 行）与账单调度的常驻缓存，预计常驻增加数 MB。32 位设备上 Dalvik 堆上限较小，卡片位图与笔记缓存需单独设上限，现 `NoteStore` 未见统一上限声明。

乙：双进程。微读若只提供数据出口，不必常开无障碍服务，进程按需拉起，常驻内存主要取决于十雨自身；微读进程在查询后进入缓存态。代价是每次查询跨进程唤醒，实测开销在毫秒级，对组件刷新足够。

## 八 发布纪律、回滚与测试成本

甲：分支随微读演进，十雨发版前需重做一次移植；回滚只能回滚十雨整包，不能回滚内置的微读版本。微读的发布纪律（`version.properties` 单一版本来源、`tools/build.sh` 的 versionCode 递增检查、release.yml 的 sha256 校验）在甲下部分失效，因为十雨的版本与微读的版本不再一一对应。测试侧，微读没有 JUnit，甲需要为内置件补测试，或在十雨侧以组件测试覆盖。

乙：两侧发版独立，回滚清晰。微读侧新增提供者可用「未安装即降级为空态」处理；十雨侧只增加一个桥接类，删除即可回退。测试成本集中在协议契约测试与两应用共存场景，微读可在自有的 `regress` 目录补一次性脚本，十雨侧新增纯 JVM 解析测试即可。

## 九 隐患与不可逆点

甲的主要隐患：卡片渲染代码与微读 UI 逻辑强耦合，移植中容易复制而非复用，形成两套逐渐分叉的实现；用户数据分叉后无法无损回写独立微读；MIT 许可允许内置，但十雨需在发布物中保留版权与许可声明，且内置件的缺陷修复要等微读上游再发版。不可逆点在于「数据副本」：一旦用户只在十雨内使用一段时间，独立微读的本地历史将落后。

乙的主要隐患：跨进程契约一旦发布就形成对外接口，后续改动需兼容；微读需长期维护数据出口；十雨需处理微读未安装、版本过旧、协议不匹配三种状态。不可逆点较轻：契约保留向后兼容即可，十雨侧可随时停止消费。

## 十 分阶段建议与最小可验证里程碑

建议先做乙，把「数据出口」作为唯一新增边界，同时用一周时间做甲的可行性探针，两者都在最小改动下验证，再由 Doow 依据实测数据拍板。

阶段 1，乙的最小验证（约 3 至 5 天）：微读新增只读内容提供者，首期只暴露周报与账单两项（数据来自 `StatsStore`、`BillStore`）；十雨新增一个只读桥接与一个组件变体，未安装微读时显示空态。验收点：两应用共存安装、十雨组件离线显示微读缓存数据、关闭微读无障碍后组件仍可用、卸载微读后十雨不崩。

阶段 2，甲的最小验证（约 3 至 5 天）：从微读仓库专用分支抽出 `CardSpec`、`CardLayout`、`CardRenderer`、`WeekCardView` 四类，作为独立 Java 库模块接入十雨，用一个组件包装渲染固定 368×346 的一帧静态卡片。验收点：十雨 release 构建通过、R8 后卡片类不被裁掉、单帧渲染与微读卡片截图逐像素比对差异可接受、APK 增量与启动耗时实测。

阶段 3，决策：若甲的最小验证显示移植差异小且增量可接受，则甲可继续；若差异主要来自数据与交互而非绘制，则乙继续扩展账单、笔记、排行三类，并把外观统一放到十雨的组件设计体系内推进。

## 十一 对比表

| 维度 | 甲 内置特供版 | 乙 数据接口加宿主消费 |

| 代码归属 | 微读仓库专用分支，十雨二次编译 | 各自仓库独立 |

| 数据归属 | 十雨内新建副本，需导入 | 微读一份，十雨只读 |
| 包名签名 | 十雨包内无签名冲突 | 两应用同存，签名不变 |
| 数据通道 | 进程内直调，无跨进程成本 | 内容提供者一次查询，约 300 行合计 |
| 无障碍 | 卡片不再依赖无障碍与桌面探测 | 卡片形态不变，微读仍持无障碍 |

## 十二 推荐

推荐乙为长期形态，理由有三。数据归属唯一，避免用户阅读历史分叉；构建与发版解耦，微读可以按自身节奏演进，十雨只维护一层桥接；十雨的组件体系已经具备自绘能力与八个微读组件，数据接入即可产出新组件，而卡片像素级复刻并不是用户可见收益的主要来源。

甲只在一种前提下成立：Doow 要求十雨内的微读卡片与独立应用视觉完全一致，且接受每次微读发版后重做一次移植。此时应从最小验证入手，先证明四类渲染代码可以在十雨 Rect 内可重复出图，再评估整体移植。

## 十三 待拍板项

1. 十雨内是否需要与微读卡片逐像素一致的视觉，还是允许按十雨组件风格重绘。
2. 用户既有微读数据是否需要与十雨共享同一份，还是允许各自独立。
3. 是否接受十雨依赖微读安装状态；若接受，未安装与版本过旧时的降级文案与入口归属。
4. 内容提供者用普通还是 signature 级权限；是否需要限制为同签名应用。
5. 账单与笔记两类派生数据是否纳入首期接口。
6. 微读是否保留无障碍卡片形态作为独立入口；两者并存时的引导方式。
7. 十雨 release 签名是否在 1.0 正式版前替换为正式密钥；两条路线都不改变该决定，但甲会让「内置件」的更新跟随十雨发版，替换签名的时间点需要一并考虑。
