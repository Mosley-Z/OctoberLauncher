# 微读墨记内置形态评估与融合方案 第二版

本文取代 `_analysis/plans/weread-embed-and-refactor-plan.md`（第一版）。第一版只给出一种方案；本版按 Doow 的第三轮拍板（负一屏即墨台、三模块默认开启、书架与最近图片可排序、遥控台仅手机端、功能与数据全保留、被删组件不做迁移、卡片按槽宽等比缩放）重新比较两种交付形态，并给出推荐与代价。

## 一、结论摘要

推荐的交付形态是**内核化双宿主**，它属于 Doow 所说的第二种路线（迭代接入），但把「接入」落成「把微读墨记逐步重构为内核加宿主适配层，原版应用与十雨内置版都只是宿主」。

这种形态满足三项硬约束：用户侧只安装十雨桌面即可获得卡片与墨台；微读墨记原版继续独立演进，既有用户不受影响；卡片视觉与交互由内核同一份代码产出，不做像素级复刻。

第一种路线（分支特供、整体 fork 进十雨）只在一种情况下可取：要求两周内出现可安装的内置版本，且接受此后双代码线并行。它的长期代价是数据副本分叉与每次微读上游改动都要重新移植，评估数据见第三节。

## 二、两种路线的边界

### 2.1 甲 分支特供

在 `D:\WorkBuddyStation\WereadMoji` 另开分支，保留完整应用，把卡片视图与数据层作为内置件交付；十雨新增组件包装层，把卡片视图放进 `WidgetView.draw` 给出的矩形。由于组件协议在进程内，Java 代码必须编译进十雨，需要新增 Java 源集或独立 Java 库模块。

代码量主体是卡片子系统约 13600 行：`CardRenderer.java` 2210、`WeekCardView.java` 736、`CardContentController.java` 705、`OverlayController.java` 889、`CardA11yService.java` 553、`A11yEventRouter.java` 856、`CardSpec.java` 392、`CardLayout.java` 298、`CardInteraction.java` 210、`NoteStore.java` 1974、`BillScheduler.java` 826、`CardPrefs.java` 723 等。

### 2.2 乙 迭代接入

微读墨记保持独立应用，同时把数据层、派生算法与卡片渲染抽成宿主无关的内核；十雨作为另一个宿主消费内核，卡片与墨台由内核渲染，数据来自本机导入或同进程调用。

纯乙（只提供内容提供者、卡片仍留在微读）不满足「内置」要求：卡片要以组件形式出现在十雨桌面，渲染必须在十雨进程内；数据若走跨进程查询，墨台三模块的聚合与排序仍要在十雨侧重写。因此乙路线在十雨一侧的工作量并不小，差别只是「代码从哪来」。

## 三、对比

| 维度 | 甲 分支特供 | 乙 内核化双宿主 |
| --- | --- | --- |
| 代码归属 | 微读分支复制一份，十雨二次编译 | 内核唯一，两个宿主各自适配 |
| 构建链 | 两套构建串联，新增 Java 源集 | 内核以库模块产出，十雨 Gradle 引入 |
| 数据归属 | 十雨内新建副本，与独立微读分叉 | 十雨内单份数据，一次导入后独立演进 |
| 卡片视觉 | 与微读卡片逐像素一致可期 | 同一份渲染代码，矩形换宿主后基本一致 |
| 无障碍依赖 | 卡片不再需要无障碍与桌面探测 | 同样不再需要 |
| 发布 | 微读每发一版要重做移植 | 内核版本号加协议版本，两侧独立发版 |
| 回滚 | 整包回滚 | 删宿主适配层即可 |
| 前期成本 | 较小，约 12 至 18 人日出可用版 | 较大，内核抽取与两宿主适配 |
| 长期成本 | 按上游改动行数计，双线并行 | 一次性重构后单线演进 |
| 不可逆点 | 用户数据副本分叉，无法无损回写 | 内核接口一旦发布需保持兼容 |

甲的主要收益是快，以及视觉上不必重新设计；代价集中在两处：数据副本，以及上游改动后的重新移植。乙的主要收益是单代码线与数据唯一归属；代价是前期要把卡片渲染与数据层从 Activity、无障碍服务、固定 480×800 坐标中解耦。

## 四、推荐的形态与理由

选择乙的内核化路线，理由有三条。

第一，功能与数据全保留的要求只有单份数据能满足。用户已有 10 个 SharedPreferences、约 2.9MB 文件数据（220 个划线文件 2.3MB、索引 77KB、书架快照 67KB、55 个想法文件 240KB），一旦内置版另起副本，两份历史会立即分叉，回写无路径。

第二，卡片在十雨桌面里不需要无障碍与桌面探测。微读卡片的 `TYPE_ACCESSIBILITY_OVERLAY`、`TomoPageGate`、`ElaHomeProbe` 与固定坐标全部作废，这部分代码本来就要重写；重写一次并沉淀到内核，比在两个分支里各留一份更省。

第三，Doow 要求「迭代而不是改造」。内核化是逐模块迁移：先数据层，再卡片渲染，再墨台，原版应用在迁移期间始终可用，每步都可独立验收。

甲的可取用法是作为验证探针：用三到五天抽 `CardSpec`、`CardLayout`、`CardRenderer`、`WeekCardView` 四类做静态单帧渲染，实测 R8 后包体增量与逐像素差异，为内核抽取提供依据。探针通过也不改变最终形态，只降低渲染适配的不确定性。

## 五、负一屏即墨台

### 5.1 模块与默认值

负一屏改成有序模块列表，五个模块：

| id | 内容 | 默认 |
| --- | --- | --- |
| `weread_bill` | 墨单：周月切换、周期导航、摘录与读书两菜单、收入三档口径、合计 | 开 |
| `weread_assets` | 阅读资产：三键排序、折叠十本、双皮肤、三条过滤、长按移出与恢复 | 开 |
| `weread_fingerprint` | 阅读指纹：四档字号、选书上限五十、485 顶点与墨量映射 | 开 |
| `bookshelf` | 现有书架卡片 | 开 |
| `negative_files` | 现有最近图片卡片 | 开 |

原微读墨记的默认掩码是 `BIT_BILL|BIT_RANK`，指纹默认关（`PagePrefs.java:90`）；Doow 要求三个模块默认开启，配置迁移时把默认列表直接写成五项。

### 5.2 排序与开关

排序即 `desktop.negativePage.modules` 的列表顺序，与现有实现一致；设置页每项提供开关与上移下移。入口放在负一屏右上角齿轮，点击进入 `Destination.NegativeSettings`；桌面偏好页现有的负一屏分组保留，作为第二入口。齿轮占用内容区高度约 44dp，需要在 `NegativeScreen` 里单独布局，不压卡片。

### 5.3 契约扩展

`NegativeModule` 增加三项：`onDestroy()`（当前 `FilesNegativeModule` 的协程只在 `onPause` 取消，销毁路径缺失）、`defaultEnabled`、`orderHint`。`NegativeHost` 增加 `context` 与 `widthDp`。`NegativePageConfig` 增加 `forms: Map<String, Int>` 与 `cardOrderInitialized`，配置版本升到 8。

### 5.4 三张卡片的内容口径

墨单、阅读资产、指纹三张卡片沿用原墨台的排版与算法，改为宽度自适应：原实现按 480×800 固定坐标绘制，迁入后按 `onSizeChanged` 给出的宽高与现有令牌推导。墨单的 13 项 `menu_*` 配置在原应用里没有用户可达界面，内置后必须在负一屏设置里补入口，否则等于丢失。

## 六、整体卡片

### 6.1 形态

卡片作为单一组件 `weread_board`，内部保留原卡片的五形态（本周、本月、本书、本记、待办），点击卡片标题区循环切换，形态写入 `NegativePageConfig.forms`，与负一屏卡片共享同一份形态选择。

### 6.2 缩放

按槽宽等比缩放：以 368×346 为基准，取槽宽与 368 的比值，字号与坐标同乘，最小可读宽度按 320dp 设下限。原实现写死 480×800 与 88×34 热区，缩放后热区按比例同步。

### 6.3 交互

原卡片靠八个触摸子窗承接点击，内置后改为声明式热区：新增 `WidgetHitRegion(x, y, w, h, action)`，`WidgetView` 增 `hitRegions()` 与带坐标的 `onLongPress(x, y)`。热区四类：标题区（切换形态）、更新于（刷新）、底部左（上一条）、底部右（下一条或打开）。长按菜单保留原有隐藏、刷新、打开墨台三项。

### 6.4 空态

未配置密钥显示「微信读书未配置」，无数据显示「暂无阅读数据」，密钥失效显示「密钥已失效」，三者都带跳设置入口。

## 七、数据层与迁移

### 7.1 存储边界

`LauncherConfig` 只放三样：密钥、桌面可见的组件形态与开关、迁移元数据。书级数据放 `filesDir/weread/` 独立文件：`index.json`（划线索引）、`nt_<id>.json`（220 个，约 2.3MB）、`ni_<id>.json`、`shelf.json`、`bills.json`、`assets.json`、`stats.json`。`menu_notes`、`menu_prices`、`menu_progress` 仍按书 id 高频写入，保留独立文件。

### 7.2 一次性导入

导入用两段式：清单（`schemaVersion=1`、来源版本、逐文件 sha256、条目数）加数据包；先写临时目录、逐项校验、再原子替换，保留七天回滚备份。超过 20MB 按 bookId 分片。

必须导入：密钥、锁屏盐与哈希、墨单手写页脚与标价、待办与编号、成就配置、本记的 taken/day/hist/cur/pick 与三槽批次。可导入：卡片与桌面偏好、12 期周账单与 13 期月账单、阅读资产、统计缓存、离线划线。可省略：书架快照、章节缓存、封面、调试日志。

密钥与数据必须同包导入，因为换钥会清空书架、进度、章节、统计与账单缓存（`StatsStore.java:12-33`），内置后清空范围还要扩到笔记类数据。

### 7.3 换钥与失效

换钥时清空 `filesDir/weread/` 下的书级数据并重建，与现有 `ContentSourceImpl.kt:170-177` 的行为对齐；导入包里的密钥与当前配置不同时，提示用户选择覆盖或跳过。

## 八、页面

内置版保留原应用的全部页面：阅读页五形态与周期选择、本书页、本记页、墨台（改为负一屏）、设置、待办、帮助。新增两页本体约 1000 至 1500 行，设置分组约 180 至 260 行。

遥控台只在手机端出现，内置版不移植，原版应用继续提供；十雨的无障碍声明不因内置而扩张。若日后要把遥控台并入十雨，`OverlayAccessibilityService.kt:113` 需要补 `flagRequestFilterKeyEvents`，且要在 S4 上确认按键派发。

## 十一、组件删减

最终保留五项：`clock`（吸收 `clock_compact`）、`calendar`、`image`、`placeholder`、`weread_board`。删除 11 项（`weread_bill`、`weread_rank`、`weread_stats`、`weread_note`、`weread_mark`、`weread_fingerprint`、`weread_covers`、`weread_month`、`koreader_month`、`reading`、`koreader` 等，以 `WidgetCatalog.kt:36-226` 的 18 条声明为准逐条核对）。旧配置的 `widgetId` 命中被删组件时改写为 `weread_board` 或 `clock`，宿主已有「未安装组件」占位，不会崩溃。图片组件改为多选与桌面点击轮播，间隔与顺序进设置声明表。

## 十二、待拍板

1. 形态：采用内核化双宿主（推荐），还是先用三至五天渲染探针再定。
2. 微读墨记仓库是否接受添加内核模块与宿主适配层，分支命名与上游合并纪律。
3. 卡片默认形态（本周）与五形态是否全保留，待办形态在无待办数据时的呈现。
4. 负一屏五项默认开关是否全部开启，书架与最近图片的默认顺序。
5. 遥控台维持独立应用，确认后内置版不涉及按键过滤权限。
6. 迁移包是否加密，以及是否允许用户选择「只导入密钥」。
7. 许可署名位置：关于页的第三方许可分组记录 MIT 与版权方。
8. 十雨 release 正式签名替换时间点，与内置版更新跟随十雨发版的节奏。

## 十三、风险

内核抽取期间原版应用仍在演进，接口会反复，需要用协议版本号与最小支持版本约束。卡片渲染从固定坐标改为按槽宽推导，视觉上可能出现一像素级差异，需要在三档设备上比对。数据导入失败要能完整回滚，导入期间的锁屏与密钥状态需要一致。内置版不再持有无障碍权限，原卡片「在其他桌面顶栏常驻」的能力随之消失，这属于形态变化的必然结果。
