## 三、格式化过程

格式化前统计方式：读取各模块 `build/reports/ktlint/**/*Check.txt`，剥离 ANSI 转义后按 `行:列: ` 计数。

| 阶段 | ktlintCheck 告警 |
| --- | --- |
| 格式化前实测 | 3215 条 |
| `gradle ktlintFormat` 自动修复后 | 15 条 |
| 手工处理后 | 0 条 |

0.9.1 报告记录的 3046 条为当时统计结果；本次格式化前实测 3215 条，增加部分来自 0.9.2 新增代码与 `feature/settings` 拆分后的文件。

`gradle ktlintFormat` 覆盖 main、test 与 kotlin script 三类源集，自动修复后变更文件 171 个（181 个源文件中的多数，剩余 10 个文件格式化前后内容一致）。排版修正只涉及缩进、换行、导入顺序与空行，逻辑、注释文字与符号名未改动。

自动修复无法处理的 15 条，逐条处理方式如下：

| 文件 | 规则 | 处理 |
| --- | --- | --- |
| `core/common/.../Json.kt` | filename | 文件仅含 `AppJson` 一个顶层声明，重命名为 `AppJson.kt` |
| `core/design/.../InkColors.kt` | property-naming | 8 条针对全大写配色令牌，跨模块以 `InkColors.PAPER` 一类形式引用，重命名会改动公共符号；文件级抑制并在文件头注释说明 |
| `feature/home/.../HomeModule.kt` | class-naming | `private object provider` 沿用模块内既有命名，声明级抑制并注释说明 |
| `feature/settings/.../BeautifyIconPanel.kt` 等 5 个文件 | no-consecutive-comments | 文件级 KDoc 与首个声明的 KDoc 相邻，文件头改写为 `//` 行注释，文字内容保留 |

5 个涉及注释头改写的文件为 `BeautifyIconPanel.kt`、`BeautifyImagePanel.kt`、`BeautifyPreviewPanel.kt`、`BeautifyThemePanel.kt`、`SettingsSpecBuilders.kt`。

格式化后复跑 `ktlintCheck`，35 份报告合计 0 条。

## 五、Android Lint 基线

`gradle check` 会触发各模块 Android Lint，当前源码存在 3 个错误与若干警告（例如 `core/device/.../PermissionCenter.kt:44` 的 `NewApi`），使 `check` 在引入静态检查之前就无法通过。处理方式与 detekt 一致：按模块建立基线，新增问题继续失败。

- 配置位置：根 `build.gradle.kts` 的 `android.library` 与 `android.application` 分支，基线路径 `config/lint/baseline-<模块>.xml`。
- 基线文件 13 份，合计 84 条存量问题。
- 生成命令：`gradle updateLintBaseline -PlintBaselineUpdate`。生成基线时通过工程属性临时关闭 `abortOnError`，其余场合保持中止。
- 首次离线执行 `check` 时 `androidx.collection:collection:1.0.0` 不在本地缓存（由 Lint 模型的 androidTest 配置引入），联网执行一次后进入缓存，随后离线执行可复现。

## 六、门禁开关

根 `build.gradle.kts`：

- `DetektExtension.ignoreFailures = false`
- `KtlintExtension.ignoreFailures = false`
- `tasks.withType<Detekt>.ignoreFailures = false`
- `check` 依赖 `ktlintCheck` 与 `detekt`，构建脚本注释同步改为「失败即中止」。

`.github/workflows/build.yml`：

- 测试步骤改为 `gradle testDebugUnitTest --continue`，与本机门禁命令一致。
- 静态检查步骤保持 `gradle ktlintCheck detekt --continue`，注释改为失败即中止；任一任务失败时该步骤返回非零，工作流失败。
- 门禁顺序仍为构建检查、测试检查、静态检查，与 `docs/15-V1.0开发计划.md` 一致。

## 八、门禁失败能力验证

临时文件在验证后删除，随后 `gradle --offline check` 恢复通过。业务代码、测试断言与既有注释内容未因格式化发生改变。
