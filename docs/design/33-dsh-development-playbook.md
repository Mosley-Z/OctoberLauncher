# 给 DSH 的开发工作手册：从功能对照到双机交付

本文把微读墨记功能集成中的实际经验整理为可重复执行的流程。它适用于本项目后续开发，也适用于把一个成熟产品的功能接入另一个宿主的工作。它不是要求照搬某一种工具，而是要求每个结论都有依据，每项修改都有明确消费者，每次交付都有可复查的结果。

## 1. 先确定用户要保留的体验

本项目的最新产品约定是：**十雨桌面独立使用微信读书数据，移植微读墨记的计算和展示规则；用户不需要安装、导入或向原 App 回写数据。** 原版代码是行为参考，不是运行依赖。不要再以“先导入原 App 数据”作为墨台可以使用的前置条件。

接到“完整集成”时，不要直接列页面和按钮。先写用户任务，例如：

- 我能在桌面看到本周成就，历史周不被当前目标污染。
- 我在 App 里选过的书，回到桌面仍然是这本；自动选择仍能回到最近在读。
- 我勾选两本指纹书、调整字号、退出和重启之后，图纸仍使用这些设置。
- 我手填的价格不会在同步后消失，移出的书能够恢复，合计与条目使用同一口径。
- 我在实验室设置的密码必须由实际锁屏服务验证。

每项任务继续拆成“进入 → 操作 → 页面结果 → 退出重进 → 进程重启 → 数据刷新”。只完成前两步，是界面接线；后面几步才验证功能闭环。

需求发生变化时及时更新边界。本次用户明确取消原 App 导入需求之后，应撤掉产品入口和运行接线，保留既有缓存。不能因为已经写了迁移代码，就继续要求用户采用迁移流程。历史实现和测试可以暂留，不能被当作当前产品能力宣传。

## 2. 建一张可以执行的对照表

建议每项功能记录以下字段：

| 字段 | 要回答的问题 |
| --- | --- |
| 用户任务 | 用户实际想完成什么？ |
| 原版依据 | 哪个文件、方法、条件和配置键定义这个行为？ |
| 当前入口 | 用户从哪里操作？ |
| 数据来源 | 哪个官方接口或本地状态提供字段？ |
| 计算规则 | 周期、累计、金额、抽样和过滤分别如何计算？ |
| 写入位置 | 确认操作写到哪里？ |
| 实际消费者 | 绘制器、执行服务、刷新器是否读同一个状态？ |
| 持久性 | 重进、重启、同步后是否保持？ |
| 双机用例 | P4、S4 分别要操作什么、观察什么？ |
| 证据与状态 | 已实现、已通过自动测试、已真机验收，分别标记。 |

不要把“有同名字段”“页面显示了值”“调用没有抛错”写成已实现。锁屏和更新问题正是这样产生的：设置页写入一份偏好，执行服务读取另一份配置；页面回显正确，实际行为不变。

即使接入唯一服务，还要查状态到 UI 的最后一步。本次“立即锁定”在真机上曾只有服务状态变化，覆盖层未展示，原因是 Activity 未订阅状态观察器。检查应一直走到 `设置 → 服务 → 状态 → 观察者 → 可见结果`，并确认观察者在页面销毁时解除。

## 3. 追完整的数据链，不凭名称猜语义

审查一项数据至少顺着以下链路走一遍：

```text
官方响应 → 适配与归一化 → 本地文件/仓库 → 共享选择状态 → 计算 → 绘制 → 用户操作写回
```

关键规则：

1. 周/月排行榜不能替代逐书累计阅读时长。周期和累计是不同数据。
2. 书架元数据不能代替真实阅读进度。当前实现用 `/book/getprogress` 补查，不从排序、最近更新时间或其他近似值推算百分比。
3. 没有拿到进度时保留缓存或显示未知，不能把未知写成 0%，更不能把请求完成时间冒充数据更新时间。
4. 书名、作者等元数据应在归一化时对齐真实书目标识，不能由当前页面碰巧选中的书来填充另一条划线的来源。
5. 笔记索引必须完整分页；“全库记录数”“合并后的条数”“当前随机批次条数”是三种不同计数。
6. 价格的未知、免费、手填价、账单价和市场价必须有明确优先级，不能用同一个零值混在一起。

查看微信读书接口时优先使用本地已配置的技能、接口适配代码及真实结构样本。只打印字段、类型和数量；密钥、划线正文和完整偏好文件不进入日志、报告、Git 或子智能体消息。

## 4. 原版源码和实际依赖必须分别核验

原版最新源码不一定等于十雨实际打包的内核。本次 `DeskPage.SEC_FP` 在 k6 中是 3；传 2 会被兼容逻辑改为资产导出。看起来都叫“分区序号”，语义却不同。

在本项目使用 Windows JDK 可直接核验公开 API：

```powershell
& 'D:\DSHStation\.toolchain\jdk\jdk17.0.20_12\bin\javap.exe' `
  -constants -classpath libs/weread-kernel-1.3.2-k6-host1.jar `
  com.inkread.weekread.kernel.desk.DeskPage
```

必要时加 `-c -p` 检查实际行为，但只分析与问题有关的方法。记录依赖文件、版本和契约；不要把“我记得这个 API 是这样”当作证据。

优先使用公开语义常量。配置的指纹开关位与内核渲染位并不相同，需要明确转换，不能把两套整数直接透传。导出尺寸同样是产品规则，不等于屏幕分辨率；指纹图纸沿用原版 480×800，预览再按屏幕等比适配。

若依赖缺少必要的编辑回调，应先评估公开 API 接法。当前 k6 价格键盘没有公开当前编辑书目，兼容桥仅集中读取固定字段，在确认前保存；对应实际 jar 字段有契约测试，发布包已有内核保留规则。以后升级内核，要把这个桥列为必查项；不能散落反射，也不能忘记 Release 的 R8 行为。

对于确认属于内核内部的缺陷，本次保留原 k6 jar，另提供宿主补丁及源码构建方法。补丁只替换 `DeskData.class`，其他条目保持原字节，并验证公开 API 不变。修改二进制依赖时必须同时交付来源、最小差异、构建脚本、摘要和验证方式；不能只给 DSH 一个来源不明的新 jar。

## 5. 一份状态只保留一个权威来源

桌面、App 内页面和墨台是同一用户状态的不同视图。不要各自存一份“当前书”“当前笔记”或“隐藏书目”。

- 共享选择应由数据层仓库提供，页面退出不丢失。
- 自动与手动选择要有明确区别，清除手动选择应真正回到自动。
- 确认和取消必须分开：弹框草稿不应边点边保存；取消后磁盘不变。
- 空集合可以是有效值。“用户明确清空”和“旧配置没有这个字段”必须能区分。
- 同步只更新联网数据，不得覆盖人工录价、待办、选择历史等用户状态。
- UI 显示成功应发生在确认落盘之后。保存失败时保留旧状态或重载撤销内存变更，并给出准确反馈。

清价和恢复隐藏项有一个容易遗漏的场景：删除新值后，旧迁移文件可能重新成为回退来源。当前用清价标记和隐藏列表的空快照表达明确删除/恢复，避免旧值回流。

## 6. 缓存必须同时设计失效方式

“每次读取最新磁盘”不等于更正确。若每本书都解析一次数百 KB 或更大的偏好文件，大书库会把一个小读操作放大成分钟级等待。本次 P4 实屏暴露了这类问题，还触发了输入超时。

先计算成本：

```text
单次解析成本 × 书目数 × 每轮计算次数 × 重绘次数
```

优先把同一轮数据作为快照读取。确实需要跨页面及时看见变更时，给文件缓存明确的失效条件：时间、长度及原子替换后的文件标识；本实例写入成功立即清缓存。读写使用已有的共享锁，避免另起一套锁后互相覆盖。

不要只测试首次读取。至少验证：

- 同实例能看见另一个写入者修改价格。
- 清价、恢复隐藏项和文件删除后，旧值不会从缓存出现。
- 同长度、相同时间戳的原子替换能够被识别。
- 普通同步写入其他字段，不丢人工编辑。

不要靠 JVM 测试里断言“必须小于 100ms”证明性能，这种阈值容易受机器影响。用真实设备记录首载、响应、是否 ANR；用行为测试证明缓存不会读旧值。

兼容旧内核时，也要测试第一笔操作：旧隐藏列表为空时，`hiddenIds()` 原实现提前返回，导致 `hideBook()` 的内存集合未被合并。已有隐藏项的测试会漏掉这个问题。补丁让空列表同样合并新隐藏项，再验证快照重建与旧项保留；不要靠写一个虚假哨兵 ID 绕过内核语义。

缓存也不能代替线程设计。此次第一次缓存优化后，首载有所改善，但录价面板仍因 `onDraw → drawDirect → current.render` 在主线程反复计算全库而 ANR。因此必须继续追到实际调用栈：绑定、测量、绘制和编辑应使用同一串行后台队列，界面消费结果；页面重建和释放需要使旧回调失效。不要在主线程用一把大锁等待后台任务，这只是把计算阻塞换成锁阻塞。

串行后台也不等于计算已经高效。本次将工作移出主线程后不再 ANR，但每个按键仍要等待全库重复扫描。核对实际源码后发现：`excerptOf` 为每本书调用一次 `loader.notes(0)`，每次重新读取 227 本笔记。补丁把整页笔记读取一次后复用，刷新时失效，保持原版摘录优先级。这个案例说明：先保证线程正确，再减少重复工作，两层都需要真机验证。

## 7. 界面完成意味着操作能够命中

墨水屏需要检查实际触点、拖动方向、长按与滚动冲突，不能只看截图。

本次可复用的检查方法：

- 弹层比例先确认变量表示“底板占比”还是“顶部位置”；70% 底板的顶部是 `height * 0.3`。
- 形态列表的绘制顺序与命中 ID 必须来自同一个过滤结果，否则会完成错误的待办。
- 拖动开始后取消父桌面的长按任务，避免慢拖被认作整理或组件选择。
- `scrollBy` 的正负方向和最小阈值需要对实际内核核验；细小移动要累计，抬手可补最后一段。
- 设置中的选书不能依赖隐藏列表页已经被测量或绘制。设置入口独立加载候选，避免刚启用模块就点选书没反应。
- 指纹候选来自笔记索引，不能把整份未读书架加入候选，制造“选了书却没有图”的体验。
- App 导航和桌面形态池不是同一范围；桌面关闭某形态，不应删除 App 的对应入口。

空态也属于功能。没有数据时说明需要同步；指纹未选书时提供选书。不要用“导入原 App”代替本项目的数据获取链路，也不要显示一个没有执行能力的开关。

## 8. 并行协作先划文件和设备所有权

本项目允许其他智能体同时开发，因此开始前先看 `git status`，记录哪些是已有修改。不要 reset、clean、回滚或格式化别人的变更来获得干净工作区。

每个子任务至少声明：

```text
目标：具体审查项及完成条件
拥有文件：允许修改的文件
禁止文件：由集成者负责的共享入口
接口约定：调用签名、状态归属、失败语义
验证职责：谁跑构建，谁操作哪台设备
交付：改了什么、没验证什么、根智能体需要接哪一行
```

源代码并行不等于构建、安装也应并行。共享 Gradle 输出由一个集成者统一管理；每台 ADB serial 同一时间只能有一个操作者。P4 与 S4 可以并行，但不能两个人同时点同一台。

子任务说“完成”时，必须追问或读取它的验证边界：是代码完成、单元测试通过，还是设备也通过。集成者负责把接口真正接上并做最终质量门禁，不能把几份“我这部分完成”直接拼成最终交付。

## 9. Windows 构建和检查的顺序

本地固定工具链的路径应记录在项目环境文档；不要使用机器上碰巧存在的另一个 JDK、Gradle 或 ADB。临时命令中不要覆盖 `$HOME` 等系统变量。

推荐顺序：

1. 阅读当前 diff 和适用约定。
2. 修改必要实现及有价值的行为测试。
3. 单独运行修改模块的 `ktlintFormat`。
4. 再运行 `check :app:assembleDebug :app:assembleRelease --offline --console=plain`。
5. 修复新增告警，不更新基线掩盖问题。
6. 安装同一个已验证 APK 到两台设备，完成实际用例。
7. 设备暴露的问题修复后，按变更范围重新检查；最后保留一次覆盖最终源码的完整门禁。

不要把 format 和 check 放在同一个 Gradle 调用中，任务图可能先检查旧格式。构建输出写到分析日志，界面只汇报有意义的失败与结果。

保留原有换行风格。尤其 Windows 上 Python 默认编码可能是 GBK，读取源码请显式 `encoding='utf-8'`，写入明确换行。最后检查 `git diff --numstat` 和 `diff --check`；一个几十行修改不应变成整文件差异。

## 10. 双机验收必须能够恢复用户状态

设备基线：P4 552×768、210dpi；S4 480×800、219dpi。两者都是低功耗墨水屏设备，模拟器顺畅不能代表真机。

安装前在私有临时目录备份 APK、应用 files 和 shared_prefs。备份可能含密钥和正文，不能进入仓库或公共报告。使用 `adb install -r`，不清应用数据。

验收每项记录：设备、APK 版本、操作、预期、实际结果、证据文件、恢复情况。至少覆盖：

- 配置变化后实际页面变化。
- 退出重进和进程重启。
- 同步之后用户编辑保留。
- 错误输入、取消、清空、恢复。
- 两种屏幕的底部按钮、弹层、滚动和触点。
- 区分内部滚动窗口与没有内滚动的完整内容：指纹不能套用资产区的高度上限，否则导出完整、列表却被截断。
- 导出保存的实际 PNG 内容与尺寸，而不只看“保存成功”提示。

临时数据只恢复测试触及的键或配置部分，合并到设备最新状态。不要为恢复一项测试设置而整体覆盖旧 tar，丢掉期间产生的新同步或用户操作。锁屏测试前必须保存原锁配置与壁纸状态，测试后恢复并确认能正常使用。

锁屏验收必须区分“输入过新 PIN”“新摘要已持久化”“正确 PIN 实际解除覆盖层”。四位输入可能自动校验，不能再盲点一次确认；二次确认对话框必须点明确的保存按钮，按返回可能只会取消。已有未知 PIN 时不要启用旧密码或猜测。仅比较新旧摘要是否不同并记录布尔结果，不输出摘要或临时密码；确认新密码生效后才做错误/正确输入测试。结束逐字段恢复原锁状态，包括失败计数与启用状态。

导航脚本不要盲点固定坐标。先截图或 XML 确认当前页面；进入菜单优先根据实际文本 bounds 定位。长任务返回 session 时先等待完成，再读截图。审批超时与命令成功是不同状态，不能假定操作已经执行，也不能无条件循环重试。

## 11. 排查顺序：先分层，再修改

当出现“页面空白”时，先区分：

```text
没有配置进列表？→ 没有构造？→ 没绑定？→ 没测量？→ 高度为空？→ 没渲染？→ 渲染太慢？→ 图是空数据？
```

本次 P4 不是简单的“没显示”，而是绑定、测量、逐书计算和绘制耗时叠加。只看第一次截图会误判成开关或布局失效。选中没有笔记的书又会造成另一种空白，因此还要检查候选的数据资格。

短期技术日志只打印阶段、耗时、尺寸、数量和异常，不打印用户内容。定位后删除频繁日志。遇到 ANR 保存技术原因，避免在旧包反复操作；修正瓶颈后安装新包重新走同一用例。

这次流程也有改进空间：应更早用大书库验证新增仓库读路径；先确认页面再执行批量坐标脚本；把“代码通过”和“设备通过”分开汇报；先完成一个可见分区的闭环，再扩大并行设备任务。不要把这些教训包装成一开始就完善的流程。

## 12. 交付报告应该说清什么

完成报告至少包含：

1. 本批范围及需求变化。
2. 用户可见的最终行为。
3. 数据和状态的权威来源。
4. 测试命令、数量、失败与跳过情况。
5. 两台设备各自实际验收的项目，未覆盖项目单独列出。
6. 用户测试状态是否恢复，最终安装版本是什么。
7. 依赖或范围限制，例如固定内核的兼容桥；本次远程翻页最终按用户要求直接移除，不能再按旧审查假设补回。
8. 是否提交、推送或发布；没有做就明确没有做。

不要用“全部适配”替代矩阵，不要把已有跳过项隐藏，不要把仍在等待设备验收写成完成。也不要为可逆本地工作反复请求确认；已经授权的开发应继续完成。真正需要用户决定的是功能范围和不可逆动作，而不是每一次格式化或安装测试包。

## 13. DSH 每次接手时的简表

```text
[ ] 确认用户最新目标，历史方案是否已被改变
[ ] 读取工作区状态，保留其他开发者修改
[ ] 找到原版规则、官方数据字段、实际打包 API
[ ] 写明当前入口 → 状态写入 → 实际消费者
[ ] 选定一个用户任务完成完整闭环
[ ] 覆盖取消、清空、重启、同步后保留
[ ] 评估书库规模下的 IO、解析和主线程成本
[ ] 格式化与检查分开执行，不新增基线豁免
[ ] 同包双机验收，明确各 serial 操作者
[ ] 保存真实图片、尺寸和技术结果，敏感信息留在私有目录
[ ] 合并恢复测试状态并确认最终版本
[ ] 报告证据、边界和后续，而不是只列改过的文件
```

持续使用这张表的价值，是让下一轮开发更快发现“接上了界面却没接上行为”的问题。功能移植的完成标准应始终落在用户的连续使用体验上。
