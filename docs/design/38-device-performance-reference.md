# S4/P4 硬件与性能设计参考

采集与整理日期：2026-10-23。适用对象为本轮两台实机及十雨1.0.29–1.0.31的测试结果。本文提供后续性能设计依据，不把设计目标、硬件字段、应用绘制和墨水面板响应混为同一指标。

## 1. 实机硬件与运行环境

本轮补读仅使用白名单getprop、cpuinfo、meminfo、CPU sysfs、wm和数据分区df，未改变设备设置。原始技术字段在本地 `_analysis/verify/device-performance-reference/hardware-2026-10-23.json`。应用内存档与WebView能力来自既有双机独立探针 `_analysis/reader-probe/s4-native-webview.txt`、`p4-native-webview.txt`。

| 字段 | S4 | P4 | 对设计的意义 |
| --- | --- | --- | --- |
| 系统/SDK | Android 11 / API30 | Android 11 / API30 | 按当前平台API和行为实现，不用新Android默认能力推断 |
| 平台/硬件字段 | rk3326 / rk30board | rk3326 / rk30board | 同平台不等于所有系统组件、面板、RAM配置相同 |
| CPU内核报告 | ARMv8 rev2，architecture8，part0xd04 | 同左 | 记录原始身份；本文不进一步猜测GPU或CPU微架构 |
| CPU拓扑 | processor0–3、possible0–3 | 同左 | 4个逻辑CPU；不能据此假定4路重型解析同时运行更快 |
| CPU0最高频率字段 | 1512000kHz（1.512GHz） | 同左 | sysfs上限，不是持续实测频率；未做热稳态/降频测试 |
| 应用可用ABI | armeabi-v7a、armeabi | 同左 | CPU为ARMv8，系统提供的应用ABI仍是32位；不假设arm64库可加载 |
| 内核可见总RAM | 2021820KiB，约1.928GiB | 3050936KiB，约2.910GiB | 两机约2/3GiB档，**不能再统称两机都是2GB**；不是厂商标称容量认证 |
| Android低内存标志 | ro.config.low_ram=true；探针lowRam=true | 同左 | P4整机RAM更多，但系统仍采用低内存档 |
| 应用memoryClass | 128MiB | 128MiB | 不能把整机RAM或瞬时空闲RAM当Java堆预算，也不能用largeHeap掩盖问题 |
| 物理像素/Android密度 | 480×800 / 219dpi | 552×768 / 210dpi | 先按实际视口布局；密度字段不是玻璃尺寸或厂商光学PPI认证 |
| 数据文件系统总块数 | 26247168个1KiB块，约25.03GiB | 同左 | 仅逻辑数据分区大小，不是整机闪存标称容量，也不证明eMMC型号或吞吐 |
| 实测WebView | com.android.webview 83.0.4103.120 | 同左 | 属软件环境，可升级变化；每轮应重查 |
| 实测Web基础能力 | columns/TextDecoder/WASM可用；Custom Highlight API、Array.at不可用 | 同左 | 固定兼容资源链；全文高亮不能直接依赖新浏览器API |

MemAvailable只是采集时快照，不用作常驻缓存额度。GPU型号、闪存类型/随机IO吞吐、电池容量/功耗、面板波形型号和温度曲线均未在本轮取得可靠数据，不从平台名或屏幕尺寸补写规格。

满屏ARGB8888位图的**设计估算**为：S4约1.465MiB，P4约1.617MiB（宽×高×4），P4多约10.4%；这是单张无额外对齐的像素量，不是实际PDF页分配。视口、裁切、allocationByteCount、共享内存及视图仍持有的位图都影响真实占用。

S4的dumpsys逻辑显示模式出现约78Hz，不能解释成EPD物理每秒刷新78次。S4存在ebc设备节点，但未取得经验证的安全完成事件/波形接口；本轮未写设备节点或调用未知ioctl。

## 2. 性能结果应该怎样读

主要验收来源：[S4](../acceptance/2026-10-23-reader-final-s4.md)、[P4](../acceptance/2026-10-23-reader-final-p4.md)、[光学](../acceptance/2026-10-23-reader-optical.md)、[整体验收](../acceptance/2026-10-23-reader-final-closure.md)。下表是历史测量，不是本次文档整理重新跑出的结果。

### 冷首屏：系统入口和引擎阶段分开

S4、4e98包/b4ee37f、每格式20次force-stop后自然外部打开，nearest-rank P95取第19项。完整端点为系统DocumentEntry START→正文成功draw；内部端点为Reader接受动作→正文draw。两者都不是摄像机看到的面板完成。

| 小样本格式 | 系统入口→draw P95 | 内部open→draw P95 | 当时目标/结果 |
| --- | ---: | ---: | --- |
| TXT，158134B | 1747.823ms | 502.648ms | 2秒，通过 |
| PDF，3页/2956B | 2173.188ms | 940.025ms | 2秒，未达到 |
| DOCX正文，1598B | 4480.703ms | 3299.545ms | 5秒，通过 |
| XLSX，17362B | 4800.479ms | 3671.761ms | 5秒，通过；单次最大5041.356ms |
| PPTX图片/表格，31672B | 6335.057ms | 5042.022ms | 5秒，未达到 |

这些是代表小样本，不是所有文件的时延上限；压缩字节数小也不代表Web初始化、XML结构、关系图和排版便宜。1.0.30修复PPTX扩展节点误识别，1.0.31修复图标失败破坏旧图，最终双机做受影响专项，未把旧包性能表冒称新包全量重测。

### 翻页、资源与大文件

| 条件 | 样本与结果 | 可采用的结论 |
| --- | --- | --- |
| S4 TXT预热相邻页复访 | 1.0.30，20次，P95 129.200ms | 仍含64KiB读取与StaticLayout重排；没有已排版页缓存，不能命名为页面缓存命中 |
| S4 PDF真实位图缓存 | 20次，P95 28.828ms | 4e98录像19条与1.0.30补1条、PDF源码不变，跨会话明列 |
| P4 TXT长会话 | 4e98，200有效翻页+30重开，P95 199.305ms | 完整样本未裁剪；最大225.175ms，P95达200ms不代表每次都达 |
| P4 CSV长会话 | 4e98，200+30，行1→4001，P95 54.726ms | 增量解析与原生窗口；不是6000行全表常驻 |
| S4 DOCX长会话 | 4e98，200+30，P95 55.902ms | 当前正文1↔2页的暖路径，不等于原版式复杂大文档全路径 |
| S4 DOCX主+绑定renderer | 翻页11点121927–128350KiB；30次关闭缓存三项零，每5次确认无绑定renderer | 按真实绑定PID合计；离散PSS不是峰值或长期无泄漏证明 |
| P4 TXT主进程 | 翻页102819–106430KiB，结束105170KiB | 先前Office/桌面共享进程的暖基线，不是冷进程基线或全进程总量 |
| S4 50MiB UTF8文本 | 52428800B首屏、唯一末尾全文搜索、99%强停恢复通过 | 64KiB窗口路线可处理此样本；单次内部首屏2138.346ms不能称P95 |
| 临时来源缓存 | 五格式冷开各20次，共100次关闭实际files/diskBytes/reservedBytes全0 | 有技术计数证据，不能因release无法run-as就推断私有缓存为零 |

HOME恢复组件后PSS可以高于阅读页面。应比较相同前后台/组件/绑定进程条件下的趋势，不把单个关闭快照增加直接定性为泄漏。

### 墨水屏光学阶段

每机20次反相棋盘翻页+20次软件manualFull；使用原片逐帧PTS、摄影运动配准，定义为区域首次可见变化→进入最终画面5%容差且持续250ms，确认窗口不加进时长。

| 设备 | 翻页P95 | 软件manualFull P95 | 3%容差敏感性（翻页/手动） |
| --- | ---: | ---: | ---: |
| S4 | 116.5ms | 902.6ms | 166.4 / 1102.5ms |
| P4 | 90.7ms | 489.6ms | 108.8 / 507.7ms |

P4原片平均约56.35fps，不能把帧号除以标称60；两端采样保守误差界S4约33.379ms、P4约36.400ms，未覆盖曝光/阈值误差。这是有限棋盘ROI，不是整屏最慢像素；两机拍摄机位/时刻不同，不据此给面板普适排名。不含触点至首次变化的等待，不能与软件P95简单相加。manualFull是产品操作名，不证明厂商波形模式或残影完全消失。

## 3. 本轮已经证明有效的优化

### 先排重复任务，再降低单次成本

原Main入栈与Activity.onResume重复调用ReaderScreen.onResume，冷启首个open被取消，实际成功sample始终为2。修复可见会话重复resume后变为sample1；后台恢复和退出generation仍保留。冷启TXT系统P95从2393.180降到2288.832ms，但内部阶段并未同步大幅变快，说明不能只盯解析代码。

随后仅跳过已知马上进入文档时不可见HOME的首次onResume取数，保留HOME View/栈、失败补恢复、返回正常resume及锁层，TXT降到1747.823ms，较初批约降低27%。PDF从同阶段2630.445降至2173.188ms。收益是相同条件不同批次的观测，不是所有入口的固定百分比承诺。

后续设计把“页面构造”“首次可见取数”“后台回来恢复”分清；不要在每次resume无条件重新打开，也不要为避重复而屏蔽真正恢复。

### 首屏不要先支付不可见页面的IO

把目录扫描、封面解码、书架/组件恢复移出文档首屏关键路径，按可见性触发。仍须保证返回时状态正确，失败路径能显示HOME，而不是用空白首屏或绕过权限/锁层换指标。书架与本书继续共用已有缓存及book入口，不为预取新增已取消的独立轮询。

### 按工作集和字节限额设计

当前实现的可复用起点如下，不是建议其他功能各自再分配一份相同预算：

| 范围 | 当前实现 | 设计要求 |
| --- | --- | --- |
| 文本 | 64KiB窗口+稀疏索引 | 不整文件decode成String；长行/emoji/编码边界测试不能省 |
| PDF | 12MiB字节LRU，按allocationByteCount计，清远邻/低内存逐出 | 当前View仍持有位图不可提前回收；隔离worker/共享内存也要计入总量 |
| 表格 | 原生20行×最多10列窗口 | 多sheet/合并区域跨窗口保持正确；搜索扫描不把全表塞进DOM |
| PPTX | 仅当前页关系闭包 | 不一次常驻全部页；母版/布局/图片关系仍须保留 |
| Office容器 | 8MiB输入、32MiB展开及结构预算 | 在昂贵解析/JS前检查，压缩大小不能替代展开/单元格/节点预算 |
| 来源临时磁盘 | 全局128MiB并计尚未展开的预约 | 退出取消与释放租约；拒绝声明超额和真实写满磁盘是不同用例 |
| 搜索 | 完整计数、最多缓存64命中，跨窗口重扫 | 不强制大DOM，不持久化查询/正文；取消使旧结果失效 |

实现入口：[SourceCache](../../feature/reader/src/main/java/com/shuiyu/octoberrain/feature/reader/source/SourceCache.kt)、[PdfViewport](../../feature/reader/src/main/java/com/shuiyu/octoberrain/feature/reader/pdf/PdfViewport.kt)、[PdfEngine](../../feature/reader/src/main/java/com/shuiyu/octoberrain/feature/reader/pdf/PdfEngine.kt)、[TextWindow](../../feature/reader/src/main/java/com/shuiyu/octoberrain/feature/reader/text/TextWindow.kt)。后续调整须先核实当前源码，避免把本文数字当永久契约。

### Web开销要按进程和宿主生命周期看

原生表格显示并不代表没有Web解析成本；DOCX/PPTX冷开主要仍有Web初始化/资源解析/排版。测主进程加实际绑定renderer，记录打开/关闭/后台分别的条件。30次关闭中renderer解除绑定、缓存归零有证据；不因此默认预热常驻WebView更好。要保留rendererGone后的可见错误及重新打开恢复，不能为了省时取消隔离或失败处理。

PPTX末个已有样本总5863.036ms：Entry→Main515.235ms，再到Displayed671.336ms，再到Web构造日志2338.919ms，再到draw2337.546ms。Web构造日志不等于解析完成；下一次若优化该瓶颈，应在同一样本补解析/布局/ready端点，不能拿两个P95相减当阶段耗时。PDF仍差约173ms，也应按现有阶段证据定位，不为小差值反复全矩阵重测。

### 性能改动必须保留状态和失败语义

重排合并最新目标尺寸，动作完成再消费；generation淘汰退出/换书后的旧回调。搜索统计不改变位置，命中真正显示后才落盘。失败图像先写独立副本、解码校验、配置读回成功后才删旧图；本轮发现“先覆盖再校验”会破坏旧有效图，不能把失败路径变快当优化。上述规则来自真实整改，不是要求加通用事务框架。

## 4. 后续功能的性能设计检查表

1. **先写端点与场景。** 冷进程/暖重开/相邻复访分开；系统入口、内部动作、光学阶段分开。说明包含哪些IO、解析、布局和进程启动。
2. **先列所有权与总预算。** Java堆、native bitmap、Web/PDF子进程、共享内存、磁盘实际文件与预约分别列。以S4低内存设备为基线，再实测P4；不要按P4整机RAM比例直接扩堆。
3. **先画关键路径。** 可见首屏最少做什么，哪些可延后；每个异步结果由谁消费，退出/尺寸改变/后台后如何取消或重新恢复。
4. **验证旧环境。** WebView83真实加载固定资源，明确替代API；release反射/压缩也必须实机可用。
5. **用同版本同条件采样。** 每条件20次P95、完整样本和失败分列；200有效翻页/30开关作为代表压力，不把边界无操作算成功。重型IO避免多路争抢，增加并发前先证明收益。
6. **按实际绑定进程取PSS。** 不硬编码renderer PID，冷暖基线分开；比较同态趋势并核退出资源释放。只采需要的技术字段，正文/PIN/全配置不进日志。
7. **只修已定位瓶颈。** 一次改一个可解释因素、复验受影响路径；本轮先消除重复open和不可见HOME取数，而非增加大缓存或换整套渲染器。
8. **保留恢复闭环。** 前后台、权限失效、renderer故障、网络失败后数据保留，以及测试字段恢复；方向必须观察实际布局，设置命令成功不等于重排已发生。

建议新功能评审至少给出：目标设备/软件版本、输入规模、首屏关键路径、分项内存与磁盘预算、取消/释放位置、测量端点与样本量、实测失败和下一步。本文不新增业务需求，也不把PDF/PPTX未达目标或后置扩展悄悄改为新一轮开发授权。
